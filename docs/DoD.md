# Багийн Definition of Done (DoD)

**Төсөл:** Бидний анхны төсөл — AI-д суурилсан зорилго ба дадал хөтлөгч веб апп
**Хувилбар:** v1.1
**Батлагдсан огноо:** 2026-09-22
**Хамрах хүрээ:** Sprint-ийн бүх хэрэглэгчийн түүх (user story) болон алдаа засвар (bugfix)

---

## 1. Алхам 1 — Багийн хэлэлцүүлэг

### 1.1 "Ажил дууссан гэж хэзээ хэлэх вэ?"

Хэлэлцүүлгийн эхэнд гарсан хариултуудыг задлан шинжилэв:

| Санал болгосон хариулт | Яагаад хангалтгүй вэ |
|---|---|
| "Код бичиж дуусахад" | Ажиллана гэсэн баталгаа алга. Зөвхөн бичсэн хүн нь л итгэлтэй байна. |
| "Миний компьютер дээр ажиллахад" | Орчноос хамаарсан алдаа (works on my machine) илрэхгүй өнгөрнө. |
| "Push хийхэд" | Ревью, тест хийгдээгүй код үндсэн салбарт орох эрсдэлтэй. |
| "PO хүлээж авахад" | Зөв боловч хэт оройтсон — алдааг хамгийн үнэтэй цэгт олж илрүүлнэ. |

**Багийн нэгдсэн дүгнэлт:**

> "Дууссан" гэдэг нь хүн бүрийн субьектив мэдрэмж биш, **баг даяар нэг ижил
> ойлгогддог, гуравдагч хүн шалгаж чадахуйц шалгуурын жагсаалт** байх ёстой.

Үүнээс гарах практик дүрэм: хэрэв нэг шалгуурыг хоёр өөр гишүүн шалгаад өөр
дүгнэлтэд хүрч байвал тэр шалгуур буруу бичигдсэн гэсэн үг. Тиймээс шалгуур бүрд
"хэрхэн шалгах вэ" гэсэн баганыг заавал нэмэхээр тохиролцов.

### 1.2 "Кодыг production руу явуулахад ямар шаардлагууд хангагдсан байх ёстой вэ?"

Манай төслийн онцлогоос (XP, Level, Streak, Virtual Pet зэрэг хоорондоо
хамааралтай тооцоолол) үүдэн дараах шаардлагуудыг тодорхойлов:

- Шаардлага хэрэгжсэн бөгөөд хэрэглэгчийн түүхийн хүлээн авах шалгуурыг хангасан
- Гар аргаар биш, **автоматаар давтагдах** байдлаар шалгагдсан байх
- Өөр гишүүн кодыг уншаад ойлгосон байх (code review)
- Алдаа гарвал буцаах (rollback) боломжтой байх — жижиг, утга төгөлдөр commit
- Дараа ирэх хүн уншаад ойлгохуйц баримтжуулалттай байх

**Онцгой анхаарах зүйл:** XP, Level, Streak-ийн тооцоолол буруу бол хэрэглэгчийн
өгөгдөл гажиж, буцаан засахад хэцүү болно. Тиймээс эдгээр логикийг гар аргаар
биш, зөвхөн нэгж туршилтаар шалгана гэж тогтов.

---

## 2. Зааварт өгсөн жишээ жагсаалт (лавлах эх сурвалж)

Лабораторийн ажлын зааварт дараах жишээг өгсөн ба багийн DoD-г үүн дээр
тулгуурлан боловсруулав:

- Код бичигдсэн
- Код нэгжийн тестлэлд ТЭГЦ давсан
- Код багийн хүнээр code review хийгдсэн
- Багийн код хандалтын дүрмийг дагасан
- Бүх оролдлого (test cases) туршигдсан
- Баримтжуулсан (ж.нь: функцийн тайлбар)
- Integration туршилт (хэрэв хамаатай бол) амжилттай

---

## 3. Багийн DoD v1.1 — батлагдсан жагсаалт

> **★** тэмдэгтэй мөрүүд нь Алхам 5-д нэгжийн тестлэлтэй холбоотойгоор
> нэмэгдсэн буюу хүчитгэгдсэн шалгуурууд.

| # | Шалгуур | Хэрхэн шалгах вэ | Хариуцагч |
|---|---|---|---|
| 1 | Код бичигдсэн, хэрэглэгчийн түүхийн хүлээн авах шалгуурыг хангасан | Story-гийн acceptance criteria-тай мөр мөрөөр тулгах | Хөгжүүлэгч |
| 2 ★ | **Код нэгжийн тестлэлд бүрэн (ТЭГЦ) давсан** | `npm test` ажиллуулахад **бүх тест ногоон**, `exit code 0`, алгассан (skipped) тест байхгүй | Хөгжүүлэгч |
| 3 ★ | Шинэ буюу өөрчлөгдсөн логик бүр нэгж туршилттай | Функц болон түүний тест нэг PR дотор хамт ирсэн эсэх | Ревьюер |
| 4 ★ | Тест нь эхлээд унаж байсан нь батлагдсан | Commit-ийн түүхэнд УЛААН (унасан) төлөв харагдах, эсвэл `results/`-д гаралт хадгалагдсан | Ревьюер |
| 5 | Код багийн гишүүнээр code review хийгдсэн | Pull Request дээр дор хаяж 1 approve | Ревьюер |
| 6 | Багийн код бичлэгийн дүрмийг дагасан | Нэршил, файлын бүтэц, форматын дүрэмтэй нийцсэн эсэх | Ревьюер |
| 7 | Бүх тохиолдол (test cases) туршигдсан | Хэвийн утга + хилийн утга + алдааны тохиолдол гурвуулан бичигдсэн | Хөгжүүлэгч |
| 8 | Баримтжуулсан | Функцийн зориулалт, параметр, буцаах утга, алдааны нөхцөл тайлбартай | Хөгжүүлэгч |
| 9 | Integration туршилт амжилттай (хамаатай бол) | Модулиуд холбогдсон төгсгөл-төгсгөлийн урсгал ажилласан эсэх | Баг |
| 10 | Үндсэн салбар эвдрээгүй | `main`-д merge хийсний дараа бүх тест давсан хэвээр байх | Scrum Master |

## 4. Алхам 5 — Нэгжийн тестлэлийг DoD-д албажуулав

Лабораторийн заавар: *"Код нэгжийн тестлэлд ТЭГЦ давсан" гэсэн цэгийг нэмж,
баталгаажуулна.*

v1.0 дээр "Код нэгжийн тестлэлд давсан" гэсэн мөр байсан боловч **хэмжиж
болохооргүй** байв — "давсан" гэдгийг хэн, юугаар шалгах нь тодорхойгүй.
Лабораторийн ажлыг гүйцэтгэх явцад олж мэдсэн зүйлсээ тусган дараах
өөрчлөлтүүдийг оруулав:

**1. Шалгуур 2-ыг хэмжигдэхүйц болгов.**
"Давсан" биш, `npm test` → бүх тест ногоон, `exit code 0`, алгассан тест
байхгүй. Ингэснээр хоёр өөр гишүүн шалгаад ижил дүгнэлтэд хүрнэ.

**2. Шалгуур 3-ыг нэмэв — тестгүй логик нэвтрэхгүй.**
Функц болон түүний тест нэг PR дотор хамт ирэх ёстой. "Дараа нь тест нэмнэ"
гэсэн амлалт практикт хэзээ ч биелдэггүйг баг хүлээн зөвшөөрөв.

**3. Шалгуур 4-ийг нэмэв — тест эхлээд унасан байх ёстой.**
Энэ бол лабораторийн ажлын хамгийн чухал сургамж. Хэрэв тест анхнаасаа ногоон
байвал тэр тест үнэхээр ямар нэг зүйл шалгаж байгаа эсэх нь батлагдаагүй.
Жишээ нь `expect(() => sum(1, 2)).toThrow(...)` гэсэн тест нь хоёр тоо тул
хэзээ ч ногоон болохгүй — харин эсрэгээрээ, хэзээ ч унахгүй тест бас адилхан
хэрэггүй.

**4. Тестийн хамралтыг шалгуур 7-д тодорхой болгов.**
Зөвхөн "ажиллаж байна" гэсэн нэг тест хангалтгүй. Хэвийн утга, хилийн утга,
алдааны тохиолдол гурвуулан байх ёстой. `sum` функцийн хувьд энэ дүрмийг
хэрэглэснээр 3 тест 11 тест болж өргөжив.

### Энэ нь багт юу гэсэн үг вэ

Энэ мөчөөс эхлэн нэгжийн тестлэл нь "цаг гарвал хийх нэмэлт ажил" биш, багийн
**бүх гишүүний хийх ажлын салшгүй хэсэг** болов. Тест бичихгүйгээр ажил
"Дууссан" баганад шилжих боломжгүй.

---

## 5. Хэрэглэх дүрэм

- Энэ жагсаалт бол **багийн ажлын гэрээ**. Дээрх шалгууруудын аль нэг нь
  хангагдаагүй бол тухайн ажил Scrum самбарын "Дууссан" баганад шилжихгүй.
- DoD-г сулруулах шийдвэрийг ганц хүн гаргахгүй — зөвхөн багаар хэлэлцэж,
  энэ файлын хувилбарын дугаарыг өсгөж бичнэ.
- DoD нь хөлддөг баримт биш. Sprint retrospective бүрт дахин хянана.
