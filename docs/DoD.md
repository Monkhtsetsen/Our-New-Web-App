# Багийн Definition of Done (DoD)

**Төсөл:** Бидний анхны төсөл — AI-д суурилсан зорилго ба дадал хөтлөгч веб апп
**Хувилбар:** v1.0
**Батлагдсан огноо:** 2026-09-22
**Хамрах хүрээ:** Sprint-ийн бүх хэрэглэгчийн түүх (user story) болон алдаа засвар (bugfix)

---

## 1. Алхам 1 — Багийн хэлэлцүүлэг

### 1.1 "Ажил дууссан гэж хэзээ хэлэх вэ?"

Хэлэлцүүлгийн эхэнд гарсан хариултуудыг задлан шинжлэв:

| Санал болгосон хариулт | Яагаад хангалтгүй вэ |
|---|---|
| "Код бичиж дуусахад" | Ажиллана гэсэн баталгаа алга. Зөвхөн бичсэн хүн нь л итгэлтэй байна. |
| "Миний компьютер дээр ажиллахад" | Орчноос хамаарсан алдаа (works on my machine) илрэхгүй өнгөрнө. |
| "Push хийхэд" | Ревью, тест хийгдээгүй код үндсэн салбарт орох эрсдэлтэй. |
| "PO хүлээж авахад" | Зөв боловч хэт оройтсон — алдааг хамгийн үнэтэй цэгт олж илрүүлнэ. |

**Багийн нэгдсэн дүгнэлт:**

> "Дууссан" гэдэг нь хүн бүрийн субьектив мэдрэмж биш, **баг даяар нэг ижил
> ойлгогддог, гуравдагч хүн шалгаж чадахуйц шалгуурын жагсаалт** байх ёстой.

Үүнээс гарах практик дүрэм: хэрэв нэг шалгуурыг хоёр өөр гишүүн шалгаад өөр
дүгнэлтэд хүрч байвал тэр шалгуур буруу бичигдсэн гэсэн үг. Тиймээс шалгуур бүрд
"хэрхэн шалгах вэ" гэсэн баганыг заавал нэмэхээр тохиролцов.

### 1.2 "Кодыг production руу явуулахад ямар шаардлагууд хангагдсан байх ёстой вэ?"

Манай төслийн онцлогоос (XP, Level, Streak, Virtual Pet зэрэг хоорондоо
хамааралтай тооцоолол) үүдэн дараах шаардлагуудыг тодорхойлов:

- Шаардлага хэрэгжсэн бөгөөд хэрэглэгчийн түүхийн хүлээн авах шалгуурыг хангасан
- Гар аргаар биш, **автоматаар давтагдах** байдлаар шалгагдсан байх
- Өөр гишүүн кодыг уншаад ойлгосон байх (code review)
- Алдаа гарвал буцаах (rollback) боломжтой байх — жижиг, утга төгөлдөр commit
- Дараа ирэх хүн уншаад ойлгохуйц баримтжуулалттай байх

**Онцгой анхаарах зүйл:** XP, Level, Streak-ийн тооцоолол буруу бол хэрэглэгчийн
өгөгдөл гажиж, буцаан засахад хэцүү болно. Тиймээс эдгээр логикийг гар аргаар
биш, зөвхөн нэгж туршилтаар шалгана гэж тогтов.

## 2. Зааварт өгсөн жишээ жагсаалт (лавлах эх сурвалж)

Лабораторийн ажлын зааварт дараах жишээг өгсөн ба багийн DoD-г үүн дээр
тулгуурлан боловсруулав:

- Код бичигдсэн
- Код нэгжийн тестлэлд ТЭГЦ давсан
- Код багийн хүнээр code review хийгдсэн
- Багийн код хандалтын дүрмийг дагасан
- Бүх оролдлого (test cases) туршигдсан
- Баримтжуулсан (ж.нь: функцийн тайлбар)
- Integration туршилт (хэрэв хамаатай бол) амжилттай

## 3. Багийн DoD v1.0 — батлагдсан жагсаалт

| # | Шалгуур | Хэрхэн шалгах вэ | Хариуцагч |
|---|---|---|---|
| 1 | Код бичигдсэн, хэрэглэгчийн түүхийн хүлээн авах шалгуурыг хангасан | Story-гийн acceptance criteria-тай мөр мөрөөр тулгах | Хөгжүүлэгч |
| 2 | Код нэгжийн тестлэлд давсан | `npm test` ажиллуулж, бүх тест ногоон болохыг харах | Хөгжүүлэгч |
| 3 | Шинэ функц бүр дор хаяж нэг нэгж туршилттай | Функц болон түүний тест файл хамт commit хийгдсэн эсэх | Ревьюер |
| 4 | Код багийн гишүүнээр code review хийгдсэн | Pull Request дээр дор хаяж 1 approve | Ревьюер |
| 5 | Багийн код бичлэгийн дүрмийг дагасан | Нэршил, файлын бүтэц, форматын дүрэмтэй нийцсэн эсэх | Ревьюер |
| 6 | Бүх тохиолдол (test cases) туршигдсан | Хэвийн утга + хилийн утга + алдааны тохиолдол гурвуулан бичигдсэн | Хөгжүүлэгч |
| 7 | Баримтжуулсан | Функцийн зориулалт, параметр, буцаах утга, алдааны нөхцөл тайлбартай | Хөгжүүлэгч |
| 8 | Integration туршилт амжилттай (хамаатай бол) | Модулиуд холбогдсон төгсгөл-төгсгөлийн урсгал ажилласан эсэх | Баг |
| 9 | Үндсэн салбар эвдрээгүй | `main`-д merge хийсний дараа бүх тест давсан хэвээр байх | Scrum Master |

### Хэрэглэх дүрэм

- Энэ жагсаалт бол **багийн ажлын гэрээ**. Дээрх шалгууруудын аль нэг нь
  хангагдаагүй бол тухайн ажил Scrum самбарын "Дууссан" баганад шилжихгүй.
- DoD-г сулруулах шийдвэрийг ганц хүн гаргахгүй — зөвхөн багаар хэлэлцэж,
  энэ файлын хувилбарын дугаарыг өсгөж бичнэ.
- DoD нь хөлддөг баримт биш. Sprint retrospective бүрт дахин хянана.
