# Архитектур — Backend ба Frontend

## Бүтэц

```
Our-New-Web-App/
├── backend/          Node + Express + TypeScript   → порт 4000
│   ├── src/
│   │   ├── index.ts        сервер асаах
│   │   ├── app.ts          Express апп (тестэд дангаар нь ашиглана)
│   │   ├── config/env.ts   орчны хувьсагчийг шалгах
│   │   ├── db/             схем, холболт  ← ӨС-тэй харьцдаг ЦОРЫН ГАНЦ газар
│   │   ├── auth/           нууц үг, token, cookie, оролт шалгах
│   │   ├── routes/         health, auth, users
│   │   └── middleware/     алдаа барих, 404, эрх шалгах, хязгаарлагч
│   ├── drizzle/            SQL миграцууд
│   └── Dockerfile
│
├── goal-app/         Next.js + TypeScript          → порт 3000
│   ├── app/                хуудаснууд
│   ├── proxy.ts            хамгаалалттай замын эхний шалгалт
│   ├── src/lib/api.ts      ← хөтчөөс backend рүү хандах ЦОРЫН ГАНЦ цэг
│   ├── src/lib/api-server.ts  ← серверээс backend рүү хандах цэг
│   └── Dockerfile
│
└── docker-compose.yml      db + backend + frontend
```

## Хоёр дүрэм

**1. Frontend ӨС рүү шууд хандахгүй.** Бүх өгөгдөл `src/lib/api.ts`-ээр
дамжин backend-ийн HTTP API-аар ирнэ. Frontend дээр ӨС-ийн драйвер,
холболтын мөр, схем байхгүй.

**2. Нууц зүйл зөвхөн backend дээр.** ӨС-ийн нууц үг, API түлхүүр бүгд
`backend/.env` дотор. Frontend-ийн `NEXT_PUBLIC_*` хувьсагч нь хөтөч рүү
бүтнээрээ дамждаг тул тэнд нууц утга хэзээ ч бичихгүй.

## Яагаад салгасан бэ

Next.js өөрөө сервер талтай тул API-г түүн дотор бичиж болох байсан.
Салгасан шалтгаан:

- **Тусад нь deploy хийх.** Frontend-ийг статик хостинг руу, backend-ийг
  өөр газар тавих боломжтой
- **Тусад нь масштаблах.** Ачаалал ихсэхэд зөвхөн хэрэгтэйг нь нэмнэ
- **Лаб 9 (Minikube).** Deployment, Service гэдэг ойлголт хоёр сервистэй
  үед л утга төгөлдөр болно
- **Хэрэглэгчийн интерфейс солигдоход** (ж.нь гар утасны апп) API хэвээрээ

**Төлбөр нь юу вэ:** CORS тохируулах шаардлага, хоёр deploy, хоёр
хамаарлын мод, мөн хуваалцах тогтмолууд (нууц үгийн доод урт гэх мэт)
хоёр талд давхардана. Эдгээрийг арилгахын тулд ирээдүйд `shared/`
багц үүсгэж болно.

## API

| Арга | Зам | Юу хийдэг |
|---|---|---|
| GET | `/health` | Амьд эсэх. **ӨС рүү хандахгүй** |
| GET | `/health/ready` | ӨС-тэй холбогдож чадаж байгаа эсэх |
| POST | `/api/auth/register` | Шинэ хэрэглэгч бүртгэх (+ шууд нэвтрүүлнэ) |
| POST | `/api/auth/signup` | `register`-ийн хуучин нэр. Хэвээр ажиллана |
| POST | `/api/auth/login` | Нэвтрэх |
| POST | `/api/auth/logout` | Гарах |
| GET | `/api/users/me` | Өөрийн мэдээлэл. **Нэвтрэхийг шаардана** |
| PUT | `/api/users/me` | Профайл засах. **Нэвтрэхийг шаардана** |

### POST /api/auth/register

```jsonc
// Хүсэлт
{ "name": "Эрдэнэбаяр", "contact": "erka@example.com", "password": "..." }
// contact нь и-мэйл ЭСВЭЛ утасны дугаар — аль нь болохыг өөрөө таана

// 201
{ "user": { "id": "...", "name": "...", "email": "...", "phone": null,
            "role": "user", "createdAt": "..." } }

// 400 — шалгалтаас унасан
{ "errors": { "contact": "И-мэйл хаяг эсвэл утасны дугаар буруу байна" } }

// 409 — аль хэдийн бүртгэлтэй
{ "errors": { "contact": "Энэ и-мэйл бүртгэлтэй байна" } }
```

`passwordHash` хариуд **хэзээ ч** орохгүй.

### POST /api/auth/login

```jsonc
// Хүсэлт
{ "contact": "erka@example.com", "password": "..." }

// 200 — сессийн cookie-г мөн хамт тавина
{ "user": { ... } }

// 401 — хаяг ЭСВЭЛ нууц үг буруу (аль нь болохыг хэлэхгүй)
{ "error": "И-мэйл/утас эсвэл нууц үг буруу байна" }

// 429 — хэт олон оролдлого (15 минутад 20)
{ "error": "Хэт олон удаа оролдлоо. ... секундын дараа дахин оролдоно уу." }
```

### PUT /api/users/me

```jsonc
// Хүсэлт — илгээсэн талбарыг нь л өөрчилнө
{ "name": "...", "email": "...", "phone": "...",
  "newPassword": "...", "currentPassword": "..." }

// email/phone-ыг хоосон мөрөөр илгээвэл УСТГАНА.
// Хоёулаа хоосон үлдэж болохгүй → 400.
// email, phone, newPassword-ийн аль нэгийг солиход
// currentPassword ЗААВАЛ шаардагдана.
```

`role`, `level`, `xp`, `streak`, `id`-г энэ зам **огт уншдаггүй**.

## Сесс, нэвтрэлт

### Token хаана хадгалагдах вэ

**HttpOnly cookie дотор** (`goal_session`). `localStorage`-д БИШ.

Жишээ заавруудад token-ыг `localStorage`-д хийж `Authorization`
толгойгоор илгээхийг зөвлөдөг. Хийхэд амархан ч нэг ноцтой нүхтэй:
`localStorage`-ийг JavaScript уншиж чадна. Сайт дээр нэг ч XSS гарвал
(гуравдагч этгээдийн script, зар, npm багцын халдлага) халдагч token-ыг
шууд уншиж авна.

`HttpOnly` cookie-г JavaScript **уншиж чадахгүй**. Хариуд нь CSRF
эрсдэл үүсдэг — хөтөч cookie-г автоматаар хавсаргадаг тул өөр сайт
манай API руу хүсэлт илгээж болно. Үүнийг `SameSite=Lax` хаана.

| Шинж | Утга | Яагаад |
|---|---|---|
| `HttpOnly` | true | JavaScript уншихгүй → XSS-д token задрахгүй |
| `SameSite` | Lax | Өөр сайтаас илгээсэн POST-д cookie явахгүй → CSRF |
| `Secure` | production-д true | Зөвхөн HTTPS-ээр явна |
| Хугацаа | 7 хоног | Refresh token хийгээгүй тул богино байлгах боломжгүй |

**Frontend-ийн хүсэлт бүр `credentials: "include"` байх ёстой.**
Frontend 3000, backend 4000 — хөтөч эдгээрийг өөр origin гэж үздэг
тул үгүй бол cookie явуулахгүй. Мартвал нэвтрэлт амжилттай харагдаад
дараагийн хүсэлт болгонд 401 ирнэ.

### Token-ыг хэрхэн болиулах вэ

JWT нь төлөвгүй: нэг удаа гаргасны дараа серверт бүртгэл үлддэггүй
тул хугацаа нь дуустал хүчинтэй. Нууц үгээ хулгайлуулсан хүн нууц
үгээ сольсон ч хулгайчийн гар дээрх token ажилласаар байх нь ноцтой.

Шийдэл нь `tb_users.token_version`: энэ тоог token дотор хийж, хүсэлт
бүр дээр ӨС дэх утгатай тулгана. Нууц үг солигдоход тоо нэмэгдэж,
**өмнөх бүх token тэр агшинд хүчингүй болно**.

### Хүсэлт бүр дээр ӨС рүү хандана

`requireAuth` нь token доторх мэдээлэлд итгэхгүй, ӨС-аас хэрэглэгчийг
уншина. Нэмэлт нэг query боловч:

- Админ эрхийг хассан нь шууд үйлчилнэ (token дээр "admin" үлдсэн ч)
- Устгасан бүртгэлийн token ажиллахгүй
- `token_version` зөрвөл таслагдана

## Эрх (permissions)

Хоёр л түвшин: `user` ба `admin`. ӨС дээр `tb_users.role` багана,
`user_role` enum-аар хадгална. Анхны утга нь `user`.

Тусдаа permissions хүснэгт үүсгээгүй — хоёр утгад тэр нь илүүц
төвөгтэй байдал.

### Эрхийг хүсэлтээр тогтоох боломжгүй

Бүртгэлийн API нь биеэс зөвхөн `name`, `contact`, `password` гурвыг
л авна. `{"role":"admin"}` гэж илгээсэн ч үл тоомсорлоно — эрх нь
схем дээрх анхны утгаар тогтоно. Үүнийг тестээр бэхэлсэн
(`backend/src/app.test.ts`).

### Хэн нэгнийг админ болгох

Эрх өөрчлөх интерфейс санаатайгаар хийгээгүй. Одоогоор ӨС дээр
гараар:

```sql
UPDATE tb_users SET role = 'admin' WHERE email = 'ta@example.com';
```

Docker compose дээр:

```bash
docker compose exec db psql -U goal -d goal_app   -c "UPDATE tb_users SET role = 'admin' WHERE email = 'ta@example.com';"
```

### Хамгаалалттай замууд

| Зам | Хэнд |
|---|---|
| `/profile` | Нэвтэрсэн хүн бүрт |
| `/admin` | Зөвхөн `admin` эрхтэйд |

Шалгалт **гурван давхаргатай**:

| # | Хаана | Юу хийдэг | Хариу |
|---|---|---|---|
| 1 | `goal-app/proxy.ts` | Cookie байгаа эсэх, backend-ээс эрхийг асуух | 307 нэвтрэх хуудас руу / 404 |
| 2 | Хуудасны сервер тал | Backend-ээс эрхийг дахин асуух | redirect / `notFound()` |
| 3 | Backend | Зам бүр дээр token, эрхийг шалгах | 401 |

Нэг давхаргад алдаа гарвал нөгөө нь барина. Гурвуулаа **сервер дээр**
ажиллана — JavaScript унтраах, DevTools нээх, API руу шууд хүсэлт
илгээх зэргээр тойрох боломжгүй.

Энгийн хэрэглэгч `/admin` руу орвол **404** (403 биш). 403 нь "энд ямар
нэг зүйл байна, чамд эрх алга" гэж хэлж өгдөг.

#### Яагаад шалгалт `proxy.ts`-д байх ёстой вэ

Энэ төсөл `cacheComponents` горимд ажилладаг: хуудасны тогтмол хэсэг
эхлээд явж, динамик хэсэг нь урсгалаар нэмэгддэг. Тэр үед HTTP статус
аль хэдийн `200` гэж явчихсан байдаг тул **хуудас дотроос 404 буцаах
оройтсон** байна — агуулга нь зөв гарах ч статус нь 200 хэвээр үлдэнэ.

Proxy нь хуудас зурагдахаас өмнө ажилладаг тул жинхэнэ статус буцаана.

### /admin ба хайлтын систем

| Арга | Юу хийдэг |
|---|---|
| `app/robots.ts` → `Disallow: /admin` | Хайлтын ботод "бүү уншаарай" гэж хэлнэ |
| Хуудасны `robots: { index: false }` | "Уншсан ч үр дүнд бүү гаргаарай" |

**Хоёул нь хамгаалалт БИШ.** robots.txt бол эелдэг хүсэлт — хортой бот
тоохгүй. Үүнээс гадна robots.txt нь ил файл тул `/admin` зам байдгийг
зарлаж өгдөг. Хамгаалалтыг дээрх гурван давхарга хийнэ.

## Локал дээр ажиллуулах

### Хувилбар 1 — Docker (хамгийн хялбар)

```bash
docker compose up --build
```

Эхний удаа схемийг ӨС рүү буулгана:

```bash
cd backend
DATABASE_URL="postgresql://goal:goal_local_dev@localhost:5432/goal_app" \
  npx drizzle-kit migrate
```

### Хувилбар 2 — гараар

Гурван терминал хэрэгтэй.

**1. ӨС:**
```bash
docker compose up db
```

**2. Backend:**
```bash
cd backend
cp .env.example .env     # эхний удаа — JWT_SECRET-ээ бөглөнө
npm install
npm run db:migrate       # эхний удаа
npm run dev              # http://localhost:4000
```

**3. Frontend:**
```bash
cd goal-app
cp .env.example .env.local   # эхний удаа
npm install
npm run dev                  # http://localhost:3000
```

Шалгах:

```bash
curl http://localhost:4000/health
curl http://localhost:4000/health/ready
```

Дараа нь http://localhost:3000/register нээж бүртгүүлнэ. Бүртгүүлмэгц
нэвтэрсэн байх тул шууд профайл руу ордог.

## Анхаарах зүйлс

**`NEXT_PUBLIC_API_URL` нь build хийх үед шигтгэгддэг.** Next.js энэ
угтвартай хувьсагчийг кодод шууд бичдэг тул контейнер асах үед өөрчлөх
боломжгүй. Docker-т ENV биш **ARG** болгон дамжуулна
(`goal-app/Dockerfile`).

**Утга нь хөтчөөс харагдах хаяг байх ёстой.** `http://backend:4000` гэж
бичвэл ажиллахгүй — тэр нэр зөвхөн Docker-ийн сүлжээнд утгатай, харин
хүсэлт хэрэглэгчийн хөтчөөс явдаг.

**Backend-ийн `DATABASE_URL` нь эсрэгээрээ.** Тэр хүсэлт контейнерээс
явдаг тул хост нь `localhost` биш **`db`** байна. Мөн шалтгаанаар
frontend-ийн **`BACKEND_INTERNAL_URL`** нь `http://backend:4000`:
Next.js-ийн сервер талаас явах хүсэлт контейнерийн дотроос гардаг.

**`COOKIE_SECURE`-ийг локал дээр `false` болгоно.** Docker compose
дээр `NODE_ENV=production` атлаа хаяг нь `http://localhost` байдаг.
`secure` cookie зөвхөн HTTPS-ээр явдаг тул үүнийг дарж бичихгүй бол
нэвтрэх боломжгүй болно. Жинхэнэ сервер дээр хэзээ ч `false`
болгохгүй.

## Хараахан хийгдээгүй

| Юу | Тэмдэглэл |
|---|---|
| Refresh token | Одоо token 7 хоног хүчинтэй. Богиносгоход refresh хэрэгтэй |
| Хүсэлтийн хязгаарын нийтлэг сан | Одоо санах ойд — олон хувилбар ажиллавал сулрана |
| И-мэйл баталгаажуулалт | Одоогоор хаягийг шалгахгүйгээр бүртгэнэ |
| Нууц үг сэргээх | И-мэйл баталгаажуулалтаас хамаарна |
| MFA | NIST-ийн зөвлөмж. Одоо зөвхөн нууц үг |
| `/dashboard` маршрут | `src/app/` дотор байгаа тул ажиллахгүй — тусад нь засна |
